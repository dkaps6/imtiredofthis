# Coverage v2 as a WR/TE Efficiency Signal — Novelty Check

**STATUS: RESEARCH ONLY.**

## Verdict

**Split verdict — neither of WR_GAP_FINDINGS.md's two clean categories is fully right. More precisely:**

- **The specific proposal in WR_GAP_FINDINGS.md / TE_GAP_FINDINGS.md — running the player-level WR-CB matchup file (`wr_cb_exposure.csv`: `primary_cb`, `shadow_flag`, `wr_cb_advantage`) through an R7/R8-style frozen, walk-forward, strictly-prior diagnostic — is CONFIRMED NEVER TRIED**, and is **structurally not walk-forward-backtestable at all** with data currently in this repo (see Evidence §3). This part of the proposal is novel, but "novel" here mostly means "blocked," not "untested by oversight."
- **The coarser, team-level half of Coverage v2 (`coverage_man_rate` / `coverage_zone_rate`, i.e. `cb_coverage_team.csv`) is CONFIRMED ALREADY TRIED AND REJECTED (near-neutral) as a receiving-yards/receptions efficiency predictor**, via a real, executed CI backtest (Evidence §2) — not merely proposed and abandoned like the WR-R* research branches, but actually run with a result already sitting in this repo's Actions history.
- **The same team-level coverage signal is already CONFIRMED IN PRODUCTION today**, but only as a static, hand-set heuristic multiplier from the pre-research "elite pricing core" era (Evidence §4), never validated through the frozen-protocol methodology WR-R* research uses.
- **R19/R22 (RB's promoted receiving-tail model) does NOT use coverage/matchup signal in any form** (Evidence §5) — it is not an existence proof that coverage data works for efficiency; if anything it's a data point that RB's most successful recent efficiency-adjacent work found other signal families (identity/room-share, xYAC-over-expected from raw PBP) instead.

## Evidence

### 1. Coverage v2's origin and purpose
`scripts/build/build_coverage_v2.py` (commit `c5463af`, 2026-08-18) is explicitly framed as an **identity + enrichment pipeline**, not a modeling experiment: "NFL identity ... comes only from the authoritative schedule ... Coverage intelligence (man/zone tendencies, WR alignment, primary CB/shadow notes) is enrichment." `scripts/run_coverage_v2.py` wires it into the Full Slate build. Consumers on `main` are `context_bridge.py`/`context_bridge_v3.py`/`team_context_v3.py` (build canonical team/player context) plus WR-R15/QB-C2 validators. So Coverage v2 itself was purpose-built as production plumbing, matching WR_GAP_FINDINGS.md's assumption — **but the underlying man/zone signal is much older**: an earlier `cb_coverage_team.csv`/`cb_coverage_player.csv`/`wr_cb_exposure.csv` trio already existed from 2025-10-27 (`build_cb_coverage_player.py`, PR #109), a full pre-research-era generation before Coverage v2 was rebuilt in Aug 2026.

### 2. Team-level coverage WAS ablation-tested against rec_yards/receptions — and it ran, with a result
`scripts/backtest/run_feature_ablation.py` (added 2026-08-19, "Backtest Migration 16") masks `coverage_man_rate`/`coverage_zone_rate`/`man_rate`/`zone_rate`/`middle_open_rate` (a `no_coverage` variant) and re-runs the full Monte Carlo projection pipeline against the 2025 season, scoring MAE/RMSE/bias per market (`pass_yards`, `rec_yards`, `receptions`, `rush_yards`, `rush_att`, `rush_rec_yards`). It is wired into `.github/workflows/backtest-walk-forward.yml`'s "Run historical feature ablation" step, and I confirmed via the GitHub Actions API that this step **actually executed successfully** in run `32316784561` (job `96270637077`, 2026-08-20T00:24–00:32 UTC, "Backtest Migration 16: add historical feature ablation harness"). The printed CI summary:

| variant | market | n | delta_mae_vs_full | feature_effect |
|---|---|---|---|---|
| no_coverage | rec_yards | 4647 | **-0.0395** | near_neutral |
| no_coverage | receptions | 4647 | **-0.0022** | near_neutral |
| no_coverage | rush_rec_yards | 5322 | +0.0467 | near_neutral |
| no_coverage | rush_yards | 5322 | +0.0037 | near_neutral |
| no_coverage | pass_yards | 473 | +0.0632 | near_neutral (just misses "helps") |

Removing team-level man/zone coverage signal from the production MC pipeline changed rec_yards/receptions MAE by essentially nothing (both inside the ±0.05 "near_neutral" band, and if anything slightly *negative*, meaning the feature was marginally *hurting*, not helping). **This is a real, already-run test of (team-level) coverage-derived signal against receiving efficiency, with a null result** — I did not find any doc or later commit that reports on this result or references it in a decision; it appears to have been generated and never written up (no `feature_ablation_summary.csv` is committed to git; I recovered it from the live CI job log via the GitHub Actions API, not from repo files).

Caveats on this evidence: (a) it's a **team-level, whole-slate ablation** (mixes WR/TE/RB, not a WR-only or YPR-dominant-subgroup-conditioned test like R7); (b) it tests removal of the **existing hand-coded `coverage_penalty` rule effect** (see §4) plus the raw man/zone team features as MC inputs together — it is not a clean "does coverage have signal in isolation" regression the way R7's Spearman/quartile-gap gates are; (c) it's one season (2025), not R7's multi-fold protocol. So it doesn't fully replace an R7-style test — but it is real evidence, already produced, pointing away from team-level coverage rate mattering for receiving efficiency in this pipeline.

### 3. The player-level WR-CB matchup fields cannot currently be walk-forward backtested at all
`scripts/backtest/audit_wr_cb_source.py` (added 2026-08-19, "Migration 15: audit historical WR-CB assignment source") checks whether nflverse participation/PBP data can reconstruct **who covered whom** historically. Its own recommendation constant, run in the same CI job: `wr_cb_source_recommendation = NO_GO_TRUE_ASSIGNMENT`, reason `on_field_defenders_and_target_receiver_available_but_no_explicit_coverage_responsibility` — i.e., historical data identifies which defenders were on the field and who the target was, but never an explicit CB-to-WR coverage assignment. `defense_coverage_type` (the field that seeds `coverage_man_rate`/`coverage_zone_rate`) is only 48.8% populated historically. The live-week `primary_cb`/`shadow_flag`/`wr_cb_advantage` fields in `wr_cb_exposure.csv` come from third-party current-slate scrapers (FantasyPoints/Rotowire) with **no historical equivalent reconstructable from nflverse** at all.

This predates and appears to be the direct basis for the WR research thread's own stop-rule ("do not infer fake WR-CB assignments from participation," first stated in ND2, `research-wr-post-m38-error-decomposition`). **Practical implication**: an R7/R8-style frozen walk-forward diagnostic using the individual `primary_cb`/`shadow_flag` fields as WR_GAP_FINDINGS.md proposes cannot be built with the data this repo currently has — it would need either (a) a paid/scraped historical WR-CB assignment dataset, or (b) a materially different backtest design that doesn't require reconstructing historical matchup assignment (e.g., testing only on current/live slates going forward, forfeiting walk-forward validation).

### 4. Team-level coverage already touches WR efficiency in production — as an ungated, pre-research heuristic
`scripts/modeling/rules_v2.py::coverage_penalty()` and `matchup_multipliers()`, consumed by `scripts/modeling/simulation_rules.py`, apply static multipliers to `rules_ypt` (yards-per-target, an efficiency quantity) and target share based on `coverage_man_rate`/`coverage_zone_rate`/shadow assignment:
```python
def coverage_penalty(yards_per_target, target_share, *, tough_shadow=False, heavy_man=False, heavy_zone=False):
    if tough_shadow or heavy_man:
        ypt *= 0.94; share *= 0.92
    if heavy_zone:
        ypt *= 1.04; share *= 1.06
    return ypt, share
```
This traces back to the **very first commit in the repo's history** (`c8c30e5`, "elite pricing core," 2025-10-10 — sportsbook-devig pricing era, predates the entire frozen-protocol research methodology by ~10 months) and was "consolidated into the canonical rules engine" on 2026-08-18 (`7e67a30`). The only tests covering it (`tests/test_modeling_rules_v2.py`) are unit/regression tests confirming the 0.94/1.04/1.06 arithmetic executes correctly — none validate that these specific coefficients are empirically correct, and I found no backtest, ablation, or research branch that ever tuned or validated this rule against actual outcomes. So: coverage data **is** already live inside WR efficiency projections today, but via a hand-set multiplier grandfathered in from a pre-research era, not via anything resembling the rigorous statistical validation R7/R8/R3 use.

### 5. RB R19/R22 (promoted receiving-tail model) does not use coverage/matchup signal
Read `scripts/modeling/rb_receiving_tail_production_adapter_v1.py` (the live R22 production adapter) and the R19 build script (`build_rb_r19_deployable_tail_scorer_refit_v1.py`, on `research-cross-position-catastrophic-casebook-v1`) in full, including every frozen feature list feeding its three component models:
- R8/R9 identity ridge: `prior_targets_pg, prior_receptions_pg, prior_target_share, prior_rb_room_share, prior_5plus_target_rate, prior_7plus_target_rate, last8_*, prev_season_*, same_team_prior_*, log1p_prior_games, ...` — 19 features total.
- R11 (high-volume state) logistic: `baseline_pred_targets, prior_rb_room_share, target_delta, r9_raw_r8_residual`.
- R16 (upside tail state) logistic: `baseline_pred_targets, baseline_pred_rec_yards, state_probability, prior_rb_room_share, r9_raw_r8_residual, frozen_ypt, identity_top20`.

**Zero coverage/man-zone/matchup fields appear anywhere in this stack.** It is entirely role-entitlement/identity-persistence based (target share, room share, historical volume), with `frozen_ypt` taken as a fixed input rather than something coverage adjusts. So R19/R22 is **not** an existence proof that coverage-derived data works for RB (or by extension WR/TE) receiving efficiency — it simply doesn't touch that data source. Separately, RB's actual recent receiving-*efficiency* work (R27D0/R27D0B/R27D0C, "YAC-quality source audit," Sept 2026) used a different, unrelated data source — nflverse PBP's native `xyac_mean_yardage`/`xyac_success` fields (expected-YAC-over-expected) — not Coverage v2's man/zone data at all. I confirmed no mention of `coverage`/`man_rate`/`zone_rate`/`cb_coverage`/`wr_cb` anywhere in that result doc.

## Implication for the WR/TE proposals in WR_GAP_FINDINGS.md / TE_GAP_FINDINGS.md

1. **WR_GAP_FINDINGS.md proposal #2 ("test Coverage v2 as the R7/R8 richer-matchup signal") should be revised, not run as originally framed.** The player-level `wr_cb_exposure.csv` matchup fields it names (`primary_cb`, `shadow_flag`, `wr_cb_advantage`) cannot be walk-forward backtested with nflverse-derived history today (§3) — there is no historical ground truth for who covered whom. Any "R7-style frozen diagnostic" built on these fields would have to either (a) commission/acquire a historical WR-CB assignment dataset first (a data-acquisition project, not a modeling one), or (b) accept a fundamentally different, non-walk-forward validation design, which would be a meaningfully lower-rigor test than R7/R8/R3's standard and should be labeled as such up front rather than run and framed as equivalent.
2. **The team-level half of the same proposal (man/zone rates) is not novel — it has already been tried, in the production pipeline itself, and the one real backtest result available (§2) is a null result.** Before investing more effort on `coverage_man_rate`/`coverage_zone_rate` specifically, it would be more efficient to (a) locate/rerun the existing `run_feature_ablation.py` harness on the current (post-M38) stack to get an up-to-date, publishable number, and (b) treat a repeat null result as reasonably strong evidence to formally close this lane, rather than reopening it as if untested.
3. **TE_GAP_FINDINGS.md's open question ("does a TE-specific coverage/matchup dataset exist?") is effectively answered: no differently than WR** — Coverage v2's player/exposure layer is WR-scoped by construction (`load_wr_universe`, `WR_SLOT_POSITIONS` in `run_coverage_v2.py`); TE would need new plumbing, and would inherit the same historical-non-backtestability problem for any player-level component.
4. **This does not touch R3's WR error-persistence finding or R19/R22's role in RB**, which remain independently exactly as characterized in the existing gap-finding docs. R19/R22 is not, and should not be cited as, an existence proof that coverage data helps efficiency modeling — it simply never tested that hypothesis.
